# Run command cost and native reuse

Measured on the development Termux Android AArch64 host, 26 October 2026.
`hyperfine` included two warmups and ten measured runs per command. These are
small local samples on a variable-load device, not general hardware guarantees.

| Command | Mean wall time | Peak memory reported by hyperfine |
| --- | --- | --- |
| `fermi run examples/cli/hello.fe` (warm native cache) | 36.4 ms | 3.3 MiB |
| `fermi run --no-cache examples/cli/hello.fe` | 371.2 ms | 100.7 MiB |
| Prebuilt Hello World executable | 12.1 ms | 3.1 MiB |

The uncached run had substantial variability (147.9 ms standard deviation), so
the approximately 10x mean improvement is evidence for eliminating repeated
native builds, not a stable speed ratio. The original pre-change baseline also
showed the same separation: roughly 395 ms for run versus 11 ms for check.

The approximately 101 MiB peak includes the native compiler process. It is not
the memory requirement of the compiled Hello World program. Warm cache reuse
removes that compiler process from repeated invocations. The first build retains
its native compilation cost; runtime arithmetic and safety checks are unchanged.

Raw development artifacts: `build/run-baseline.json` and
`build/run-cache-benchmark.json`. Reproduce from the repository root:

```sh
./build/fermi build examples/cli/hello.fe -o build/hello-run-benchmark -O2
./build/fermi run examples/cli/hello.fe
hyperfine --warmup 2 --runs 10 \
  './build/fermi run examples/cli/hello.fe' \
  './build/fermi run --no-cache examples/cli/hello.fe' \
  './build/hello-run-benchmark'
```

Correctness is checked independently of timing by the run-cache integration
suite. It verifies executable reuse and invalidation without fragile millisecond
thresholds.
